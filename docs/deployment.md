# Production foundation — not deployed

This runbook prepares a Vercel frontend, a paid Render backend container and Supabase PostgreSQL/private Storage. No provider resources were created, existing files copied, live storage calls made, or production migrations executed by this task. Domain, region, budget, backups, secrets and provider approval remain operator decisions.

## Configuration and networking

Use `deploy/production.env.example` on the backend and `deploy/frontend.env.example` on the frontend; all secret placeholders are empty. Never copy the developer `.env` into an image. Local uses the existing `.env`; explicit `ENVIRONMENT=test` or `production` loads process variables only through `get_settings`. Production rejects debug/test providers, insecure cookies, missing trusted origins, wildcard hosts/proxies, local durable storage, missing storage credentials, predictable example signing secrets and database TLS without a CA file. Generate a random signing key of at least 32 characters. Model representations and startup errors omit secrets.

`deploy/test.env.example` describes an explicitly isolated test process. Supply variables through the runner/secret environment, not by overwriting the existing `.env`. No template authorizes test-database resets. The frontend treats a production Next build as production by default; a deliberate local-only build may use `JOBPILOT_DEPLOYMENT=local` and an explicit local API URL.

Choose one public browser origin, e.g. `https://app.your-domain.example`, and set it identically in `JOBPILOT_APP_URL` and `CORS_ORIGINS` (no trailing slash). Set `ALLOWED_HOSTS` to exact application/backend hostnames, including the Render service hostname used by probes. The backend checks Host, but Host alone is not authentication. The frontend's **server-only** `JOBPILOT_BACKEND_ORIGIN` is the HTTPS API origin; `NEXT_PUBLIC_API_URL=/api`. External [Vercel rewrites](https://vercel.com/docs/routing/rewrites) keep browser requests/cookies on the frontend origin. Do not use separate browser-facing API origins: the CSRF cookie is host-only and read by the frontend. Secure, HttpOnly refresh cookies and SameSite=Strict remain unchanged. Verify cookie forwarding, refresh/logout and file uploads at the deployed proxy before launch; these have not been live verified. No wildcard CORS or shared parent-domain cookies are introduced.

Vercel documents a 120-second external rewrite timeout; keep feature timeouts below the entire request budget and preserve ambiguous-send handling if the proxy times out. Test a maximum-sized permitted CV through the deployed rewrite; function upload limits are not proof of an external rewrite's upload behavior. Do not add a body-buffering serverless proxy function without re-evaluating limits. [Proxy limits](https://vercel.com/docs/limits).

`JOBPILOT_PROXY_IPS` defaults empty: forwarded headers are ignored. Only configure exact trusted proxy IPs/CIDRs after identifying the actual ingress path; never `*` or internet-wide networks. Untrusted `X-Forwarded-For` must not affect account throttles. With proxy trust disabled, users may share a proxy IP allowance: this is safe but not suitable for broad public registration. Establish authenticated/protected ingress and a trustworthy client-IP chain plus edge abuse controls before public launch. A Vercel rewrite followed by Render ingress has multiple hops: do not simply trust all Render/Vercel-looking header values. Application logging omits IPs entirely.

Use a dedicated runtime database role with only needed DML permissions and a separate migration credential in the release job. Disable Supabase's Data API for JobPilot tables; the app does not use Supabase Auth. Review `deploy/supabase-api-lockdown.sql` with the migration owner as defense in depth. Do not publish anon/authenticated grants to application tables. Keep the Storage bucket private, with no public/anon read policies. The server Storage service-role key bypasses RLS, so owner enforcement is in the API; never send that key to the browser. [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

For this persistent API use a direct Postgres connection, or the IPv4 **session** pooler when needed. Copy the exact host/user/port from the dashboard. Do not use transaction pooling without a separately reviewed driver/session-state change. Set `POSTGRES_SSLMODE=verify-full` and mount the dashboard CA at `POSTGRES_SSLROOTCERT`; verify the selected endpoint's certificate chain. [Connections/TLS](https://supabase.com/docs/guides/database/connecting-to-postgres). Current pool ceiling is `instances × workers × (DB_POOL_SIZE + DB_MAX_OVERFLOW)`; defaults are 1 × 1 × (5 + 0). Reserve additional connections for release jobs, administration and provider services. Check the actual compute tier's database and pooler limits before scaling; they are not universally constant. [Compute](https://supabase.com/docs/guides/platform/compute-and-disk).

Disabled SMTP, Gmail and AI do not block startup or manual profile/CV/job features. Registration/recovery cannot deliver email until SMTP is configured. Enabled account email must use the trusted app URL. Configured Gmail redirect and settings URLs must use that same origin; preserve the encryption key securely across deployments. Optional provider availability is checked by its feature, never by readiness.

## Build, release and readiness

1. Frontend: set the frontend variables; run `npm ci` and `npm run build` from `frontend`. Select Next.js on Vercel, root `frontend`. Never define backend secrets as `NEXT_PUBLIC_*`.
2. Backend: build from repository root with `docker build -t jobpilot:<commit> .`. The image runs as UID 10001. Supply runtime secrets via the host's secret settings and mount the database CA. Start command is `python -m app.production`, using Render's `PORT`, one worker, no auto-migrations and no raw access logs.
3. Before enabling traffic, take independently verified database and file backups. Run **one** paid Render pre-deploy/release command: `python -m app.release`. It serializes Alembic upgrades with a database transaction advisory lock and bounded lock wait. Never launch Alembic separately in every worker. This task did not run the release command against any database. Migration rollback depends on each migration; some intentionally prohibit downgrade. Inspect generated SQL and expand/contract compatibility before a future release.
4. Configure Render HTTP health check `/api/ready`. `/api/health` is process liveness; readiness checks DB reachability and exact Alembic head. A missing/stale schema returns 503. Storage and optional providers are deliberately not contacted by every health probe. [Render health checks](https://render.com/docs/health-checks).
5. Authorized post-deploy checks must verify login/refresh/logout, owner isolation, private upload/download/delete, SMTP and optional integrations separately. A healthy readiness response does not prove them.

The Python base image is pinned by digest and Linux runtime dependencies by `backend/requirements-production.txt`; update them deliberately with affected tests and vulnerability review. The frontend uses its existing lockfile. Registry/package downloads during local builds are not live application-provider verification.

Each API response carries a new server-generated `X-Request-ID`. Production logs retain only request ID, the fixed route name, status and duration, omitting URLs, query strings, headers, identities, bodies, tokens and exception details. Validation errors omit submitted values; unexpected errors return a generic message. The production entry point suppresses SDK/HTTP/SQL debug output. Keep platform request-body logging, APM payload capture and frontend analytics on account/mailbox pages disabled; review platform edge query logging for OAuth callbacks. Those external logging controls remain a launch dependency. Platform stdout is not a private backup or diagnostic store.

## Private file cutover — dry run first

Local development keeps UUID-named files under `RESUME_STORAGE_DIR`. Production uses only the configured Supabase bucket with keys `resumes/<resume UUID>`. There is no automatic local fallback or provider-switch migration. The adapter checks bucket privacy before operations, bounds response size/time, does not follow redirects, preserves bytes and never returns public/signed links. Downloads authenticate and look up the owned database record before contacting storage. A failed deletion retains the database record for retry. Database and object deletion are not one atomic transaction: a DB failure after object deletion can leave missing bytes; a failed upload/DB commit can leave an orphan. Reconcile using inventories and restore from backups; never silently claim these are atomic.

Configure the server-only service-role key and a bucket accepting `application/octet-stream` with a size allowance matching the application. The REST contract follows the [Storage reference](https://supabase.com/docs/reference/self-hosting-storage); bucket metadata GET was also verified against the [official client implementation](https://github.com/supabase/supabase-js/blob/master/packages/core/storage-js/src/packages/StorageBucketApi.ts). No live contract test has been performed.

From `backend`, run `python -m app.storage_inventory > ../storage/file-inventory.json`. This opens a read-only DB transaction, reads local files, records UUID/size/SHA-256/proposed object key, and counts unreferenced UUID files. It never contacts Storage or changes files/rows, and omits filenames/CV text. Keep the manifest private. Review missing files, symlinks, size mismatches and orphan counts before copying anything. The procedure is implemented and tested with synthetic files; existing files have not been moved or deleted.

For a separately authorized cutover: pause uploads/deletes, back up both stores, produce the manifest, copy each original byte stream without upsert to the private target, download and compare every SHA-256 and size, and record discrepancies. Verify owned/foreign-user access and anon denial. Only after all referenced files are accounted for may the deployment switch `JOBPILOT_STORAGE`. Keep the source read-only until the rollback window expires. No automated copy/delete tool is shipped in this task. Do not change the setting first and discover missing CVs afterward.

Reviewed extraction text, pack versions, approved email attachment snapshots and interview snapshots are stored in PostgreSQL. Generated PDF/DOCX exports are rendered from those records on demand; they are not dependent on a durable local export directory. Back up the database as sensitive document storage too.

## Backup, restore, retention and rollback

Supabase database backups **exclude Storage object bytes**. Pro includes managed database backups subject to the selected plan's retention; use a separate encrypted object backup and matching manifest. [Backup scope](https://supabase.com/docs/guides/platform/backups). Define RPO/RTO with the operator; proposed initial targets (not achieved claims) are daily DB/file backups, 30-day encrypted retention and quarterly isolated restore drills. If daily loss is unacceptable, budget PITR and a compatible object version/backup process.

Database procedure: use `pg_dump --format=custom --file=<private-backup>` with credentials in a private passfile/secret environment, TLS verification and no password in command history. Copy object bytes through an authorized server-side backup process to a separate private encrypted location; include manifests, application version, Alembic revision, ownership metadata and cryptographic-key recovery instructions. Keep signing/mailbox encryption keys separately access-controlled; losing the mailbox key makes stored OAuth credentials unusable. Restrict backup access and test key recovery.

Restore only into a **new isolated target**: restore the DB dump with `pg_restore`, recreate a private bucket, restore bytes at exact keys, verify all hashes/counts and database references, then verify owner denial and download behavior with disposable users. Never restore over the current persistent development/test/production database as a test. Reconcile external sends/replies after point-in-time restore; do not resend queued/unknown applications automatically. No backup or restoration was performed or tested here.

Rollback means redeploying a schema-compatible prior image and routing traffic deliberately. Do not downgrade data-bearing migrations or switch back to local storage if post-cutover objects only exist remotely. Restoring an older DB can lose newer records and disconnect them from object versions: require an explicit maintenance/reconciliation plan.

Account deletion and bounded retention now use the reauthenticated Settings flow and separately scheduled cleanup command in [Account data controls](account-data.md). Do not delete a user row directly: private files, provider revocation and backup suppression require coordinated cleanup. Configure the scheduler, final retention policy and an external restore-time deletion ledger before launch. No backup restoration or live provider deletion has been verified.
