Built on `e3b724c`. JobTech remains available; **Jobicy** is the only added provider. No account creation, credentials, paid subscription, scraping, AI, email or application sending is needed for discovery.

## Behavior and data interpretation

Select a source, search, preview, then explicitly import. The signed 15-minute preview remains owner-bound. Existing saved-job uniqueness uses `(owner, source, external ID)`, so equal IDs from different sources are distinct. Repeat imports return the original owned job without changing title, notes, edits or archived state. Original attribution/link and normalized snapshot remain visible on the saved-job page; existing fit/pack/tracking workflows receive an ordinary saved job.

Cross-source warnings compare current saved title/company case-insensitively after trimming, only within the current owner, and link at most five candidates. They are **possible matches**, not confirmed duplicate vacancies. Separate postings, repeated hiring rounds and identical titles can be distinct; import never auto-merges them. This intentionally conservative heuristic misses renamed companies/edited titles and does not deduplicate manually saved unattributed records.

Jobicy keywords and applicant-region text are **local substring filters on the latest 100 cached listings**, not unrestricted provider-wide search or invented geography slugs. For example, `Lebanon` does not match a source label of `EMEA`; that broader label does not prove Lebanese eligibility. Unknown regions fail a nonempty region filter. The remote checkbox is fixed on for Jobicy because the source describes these as remote listings. JobTech keeps its approximate remote filter; structured location filtering is unavailable there, so use its keywords. Salary filtering is not offered.

`remote_arrangement` is distinct from `applicant_region`. Jobicy's eligibility string is displayed as supplied (including “Anywhere” when explicitly supplied), with employer-verification guidance. Missing eligibility stays unknown; remote alone never becomes worldwide. Worksite location is not inferred from applicant-region text. Missing salary, currency, interval and closing date are labelled honestly. HTML descriptions become bounded plain text; scripts/styles/frames are discarded and React escapes displayed content. No logo/image URLs or application URLs are fetched.

## Operational bounds and setup

No new secret or environment setting is required. Existing `JOBPILOT_DISCOVERY_ENABLED` controls discovery; `JOBPILOT_DISCOVERY_TEST_PROVIDER` remains false outside guarded tests. Apply additive migration `c0d1e2f3a4b5` through the normal single-release migration procedure before starting this version. It creates only the global public `discovery_cache` table. It changes no saved-job fields or existing rows. The cache is not candidate/account data and is intentionally excluded from account export/deletion.

Provider code (`jobicy_provider.py`) owns only HTTP/parsing. `discovery_catalog.py` manages the shared database cache; `discovery_service.py` alone imports owned saved jobs. One global Jobicy row holds at most 100 normalized listings and 20 availability outcomes. Shared row locks and a committed attempt timestamp prevent worker/restart polling bursts. A failed/interrupted catalog fetch cannot retry until the next hourly window; stale content is not silently served. Refresh occurs only on an explicit user search/preview after that window, not in a background loop. Cache content is replaced, never accumulated into a historical source database.

The GET endpoint is fixed to `https://jobicy.com/api/v2/remote-jobs?count=100`. No taxonomy query is needed because the region filter uses actual returned text, not stored API slugs. Pagination uses 20 local results per page and stops at the cached catalog boundary. A zero-result filter is not proof that the provider has no such vacancy elsewhere.

Preview performs a documented HEAD availability check using only a canonical Jobicy `/jobs/<matching numeric ID>-<slug>` URL from the cache. Arbitrary caller URLs, foreign hosts, userinfo, query strings, encoded paths and redirects are rejected. Each listing is checked at most once per catalog; at most 20 explicit checks are allowed globally per hourly catalog. A durable pre-I/O claim prevents duplicate checks after crashes. `404`/`410` blocks preview and hides that cached item; other failures remain rate-limit/unavailable/invalid states. Absence from the latest catalog is not labelled definite expiry. A vacancy may close after preview; a saved snapshot is not a continuing availability guarantee.

I/O has an eight-second HTTP timeout, two-megabyte decoded-response bound, 15-second streaming deadline checked between chunks, zero retries and no provider fallback. Required-field/type/length errors fail visibly rather than silently omitting malformed listings. Provider bodies/headers are not logged. Global preview allowance and strict parsing can limit usability; evaluate production load before increasing limits or arranging higher-volume access.
